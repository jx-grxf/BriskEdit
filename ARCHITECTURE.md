# BriskEdit Architecture

This document describes how BriskEdit is put together: the modules, the data flow from a keypress to a pixel, the threading model, and the rules every layer follows.

For decisions that shaped the architecture (editor backend choice, toolchain discovery, plugin model), see the ADRs in [`docs/`](docs/).

---

## Module layout

BriskEdit is a SwiftUI macOS app project generated by [`xcodegen`](https://github.com/yonaskolb/XcodeGen) from `project.yml`. The Xcode project itself is not committed.

```
Sources/BriskEdit/
├── App/           ← @main, scene composition, AppCommands menus
├── Workspace/     ← WorkspaceModel, file tree, tabs, file-node listing
├── Editor/        ← AppKit editor host, NSTextView subclass, gutter, theme
├── Document/      ← TextDocument value/state, file IO
├── Commands/      ← Command palette + command registry
├── Settings/      ← Settings scene, Preferences store
├── Updates/       ← Sparkle controller, update channel
└── Resources/     ← Assets.xcassets (icons, accent colors)
```

The boundary that matters most: **AppKit lives in `Editor/` and `Workspace/` only**. The rest of the app is pure SwiftUI + Foundation, so the editor backend can be swapped (TextKit 2 → custom rope/piece-table renderer in a later milestone) without touching the workspace or command layer.

## Data flow: from a keystroke to a saved file

```
   ┌─────────────────────┐
   │ User types a char   │
   └──────────┬──────────┘
              │
              ▼  AppKit responder chain
   ┌─────────────────────────────┐
   │ BriskCodeTextView           │  TextKit 2
   │  ├─ NSTextLayoutManager     │  layout, line fragments
   │  ├─ NSTextContentStorage    │  text buffer
   │  └─ LineNumberRulerView     │  gutter, self-observes change/scroll
   └──────────┬──────────────────┘
              │ NSTextViewDelegate.textDidChange
              ▼
   ┌─────────────────────────────┐
   │ TextKit2EditorHost          │  @MainActor
   │  .Coordinator               │
   │  → document.applyEdit(...)  │
   └──────────┬──────────────────┘
              │
              ▼
   ┌─────────────────────────────┐
   │ TextDocument                │  @Observable, @MainActor
   │  ├─ text: String            │
   │  ├─ isDirty: Bool           │
   │  └─ encoding: String.Encoding│
   └──────────┬──────────────────┘
              │ when ⌘S
              ▼
   ┌─────────────────────────────┐
   │ TextDocument.save()         │  detached task
   │  └─ atomic write off-main   │
   └─────────────────────────────┘
```

A single edit fans out to the document model on the main actor; persistence detaches to a background task for the actual write. The view re-renders from the published `isDirty` flag.

## State and concurrency

```
@MainActor                          @MainActor                    detached
┌───────────────┐   binds    ┌───────────────────┐   awaits   ┌──────────────┐
│ WorkspaceModel│ ──────────▶│ TextDocument      │ ─────────▶ │ File IO      │
└───────────────┘            └───────────────────┘            └──────────────┘
       ▲                              ▲
       │ FocusedSceneValue            │ @Bindable
       │                              │
┌──────┴───────┐              ┌──────┴──────────────┐
│ AppCommands  │              │ TextKit2EditorHost  │  NSViewRepresentable
│  (menus)     │              │  + Coordinator      │
└──────────────┘              └─────────────────────┘
```

Rules:

- **`WorkspaceModel`** is `@MainActor` and `@Observable`. Holds the workspace root URL, the open tab list, and the active tab id. SwiftUI binds to it directly; there is no `ObservableObject` / `Combine` plumbing.
- **`TextDocument`** is `@MainActor` and `@Observable`. Owned by a tab. All mutation goes through `applyEdit(text:)` or `save()` — no direct property writes from views.
- **File IO** uses `Task.detached(priority: .userInitiated)` for both load and write. The String snapshot is captured by value, so the main actor never blocks on the disk.
- **`TextKit2EditorHost.Coordinator`** is `@MainActor`. It is the only thing that listens to NSTextView notifications, which keeps the UI/AppKit boundary thin.
- **Swift 6 strict concurrency** is enabled. Sendable conformance is required for anything crossing actor boundaries — `FileNode`, `EditorTheme`, and the `RunService` job descriptors are explicitly `Sendable`.

There is no `Combine` and no `async let` fanout in the hot path. The editor pipeline is single-threaded on `@MainActor` by design — typing latency is the metric we optimise for, not throughput.

## The editor pipeline in detail

### 1. TextKit2EditorHost (`Editor/TextKit2EditorHost.swift`)

The single live editor. `NSViewRepresentable` that builds a scroll view around a `BriskCodeTextView` (`NSTextView(usingTextLayoutManager: true)`) plus a `LineNumberRulerView` gutter. This file *is* the editor pipeline — the older `EditorHost`/`VisibleEditorHost`/`CodeTextView` experiments were deleted; do not resurrect them. The text view is wired to a TextKit 2 stack:

- `NSTextContentStorage` owns the text buffer, `NSTextLayoutManager` does layout into a single `NSTextContainer`.
- `widthTracksTextView = true` for soft-wrap.
- Rich text, link detection, smart quotes, auto-correct, smart-insert/delete: **all off**. This is a code editor, not Pages.
- Tab key inserts spaces when `theme.usesSpacesForTabs` is true (default), respecting `theme.tabWidth`; `insertNewline` carries indentation and opens brace bodies.
- Auto-closing of brackets/quotes, a floating `CompletionPopup` (snippets + clangd + keywords + buffer symbols), and regex syntax highlighting (`TextKit2SyntaxHighlighter`, debounced) all live in the `Coordinator`.
- `usesFindBar = true` + `isIncrementalSearchingEnabled = true` → ⌘F drops the standard AppKit find bar without us reimplementing it.

### 2. LineNumberRulerView (`Editor/LineNumberRulerView.swift`)

`NSRulerView` subclass. Hooked to the scroll view's vertical ruler slot.

Drawing strategy:

1. Iterate the document's `NSTextLayoutFragment`s starting from document start.
2. Skip fragments above the visible rect; stop iteration when past it.
3. For each fragment, count newlines from the document start to the fragment start (once per repaint, cheap on typical files; will switch to a cached line-index in MVP-1 for million-line cases).
4. Draw the line number in the gutter at the y of the first line fragment.

Redraws are triggered by `NSText.didChangeNotification` and `NSView.boundsDidChangeNotification` on the scroll view's content view. The ruler is installed by `TextKit2EditorHost.makeNSView` (`scrollView.verticalRulerView`); it self-observes and only needs theme changes forwarded via `setTheme`.

### 3. Coordinator (inside `TextKit2EditorHost`)

`NSViewRepresentable` glue lives in the host itself:

- `makeNSView` builds the scroll view, text view, and ruler once. It seeds the text view's string from the document and warms up clangd for C/C++.
- `updateNSView` forwards theme changes and re-applies highlighting. It only re-seeds `textView.string` when `document.revision` advanced *outside* this editor (cheap counter compare, not whole-string), so external edits/reloads land without a feedback loop. Tab switches force-rebuild via SwiftUI `.id(activeTab.id)`.
- `Coordinator` listens to `NSTextViewDelegate.textDidChange` and pushes `tv.string` back into the document via `applyEdit`. This is the only writer.

### 4. TextDocument (`Document/TextDocument.swift`)

The value model. No NSTextStorage, no NSAttributedString in the public surface — just `String`, `URL?`, `String.Encoding`, and `isDirty`. Loading uses `String(contentsOf:usedEncoding:)` so we round-trip the detected encoding back on save.

## UI shell

```
BriskEditApp
├── WindowGroup("workspace") → WorkspaceWindow
│   └── NavigationSplitView
│       ├── sidebar: FileTreeView          ← when a workspace root is set
│       └── detail:  EditorTabsView
│           ├── TabStrip
│           ├── EditorHost                 ← per active tab, `.id(tab.id)`
│           └── StatusBar
├── Settings → SettingsScene
│   ├── EditorPreferencesView (font, indent)
│   └── UpdatePreferencesView (Sparkle channel, auto-check)
└── .commands { AppCommands } → File / Edit / Selection menus
```

### WorkspaceWindow (`Workspace/WorkspaceWindow.swift`)

The single-window surface. `NavigationSplitView` because that is the macOS-native sidebar/detail split that resizes, collapses, and remembers width without us writing it.

When no workspace root is set, the sidebar shows a `ContentUnavailableView` with an "Open Folder…" call to action. When no tabs are open, the detail surface does the same with "New File" / "Open File…".

### Command Palette (`Commands/CommandPalette.swift`)

`⇧⌘P` shows a sheet over the workspace window. The `CommandRegistry` holds a static `[EditorCommand]` array — every entry is `(id, title, group, shortcut, perform: (WorkspaceModel) -> Void)`. Filtering is a case-insensitive substring match on title/group.

The palette is the source of truth for "things the app can do". Menu items in `AppCommands` are a curated subset — adding a new command to the registry exposes it via palette automatically; the menu surface is a separate, deliberate choice.

### Updates (`Updates/UpdateService.swift`)

Wraps `SPUStandardUpdaterController` from Sparkle. Channel selection (`stable` / `beta`) is persisted in `UserDefaults` and surfaced via a delegate's `allowedChannels(for:)`. The release pipeline writes the appcast.

`SUFeedURL` and `SUPublicEDKey` are injected at build time via Info.plist build settings, not hardcoded.

## Run pipeline (planned, MVP-1)

```
   User clicks Run (or ⌘R)
            │
            ▼
   ┌──────────────────┐
   │ RunService       │   detects language from file URL + content shebang
   │  └─ Resolver     │   walks toolchain table → ResolvedToolchain
   └─────┬────────────┘
         │
         ▼
   ┌──────────────────┐
   │ Workspace        │   workspace-local briskedit.run.json overrides
   └─────┬────────────┘
         │
         ▼
   ┌──────────────────┐
   │ TerminalSession  │   spawns the resolved command in an SwiftTerm PTY
   │  (output tab)    │   captures stdout/stderr/exit, never blocks UI
   └──────────────────┘
```

Run resolution is pure (`(URL, FileSystemSnapshot) -> ResolvedToolchain`) so it is testable without spawning processes. Execution is the side-effect at the edge.

## Release pipeline

Two GitHub Actions workflows:

- `ci.yml` — runs on every push and PR. Regenerates the Xcode project, builds Debug, runs tests, verifies the resulting app bundle signs cleanly (ad-hoc).
- `release.yml` — fires on tags (`v*`). Builds Release, packages a DMG (`script/package_dmg.sh`), produces Sparkle ZIP + appcast (`script/create_sparkle_assets.sh`), verifies the appcast, optionally notarizes + staples + validates when `BRISKEDIT_NOTARY_ENABLED == 'true'`, attaches everything to the GitHub Release.

Release runbook: [`docs/release.md`](docs/release.md).

## Invariants worth knowing

- **`updateNSView` only re-seeds `textView.string` on an external revision bump.** It compares `document.revision` against the last value the coordinator synced; equal means the change originated in this text view, so it is skipped to avoid a feedback loop. Tab switches use SwiftUI `.id(tab.id)` to force a fresh `makeNSView`.
- **`TextDocument` is the only writer to its own `text`.** Coordinator calls `applyEdit(text:)`, not direct assignment. Future undo/coalescing logic hangs off that single method.
- **File IO is always detached.** `save()` and `load(from:)` both run on a detached task. The main actor never blocks on disk.
- **No background filesystem watcher in MVP-0.** Reload-on-external-change lands in MVP-1 with FSEvents.
- **Sparkle keys are build-time secrets.** `BRISKEDIT_SPARKLE_PUBLIC_KEY` and `BRISKEDIT_SPARKLE_PRIVATE_KEY` only exist in CI secrets and a developer's local keychain. The committed `project.yml` references the env var, never the value.
